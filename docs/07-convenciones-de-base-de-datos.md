# 07 Convenciones de base de datos

Reglas de implementación para PostgreSQL a través de los modelos Django. Se aplican a las entidades de los 11 módulos descritos en [06 Modelo de datos](06-modelo-de-datos.md).

## Naming y esquema

| Regla | Ejemplo |
| --- | --- |
| **Un esquema de PostgreSQL por módulo**, mismo nombre de dominio en español: `catalogo.material`, `ventas.pedido_venta`, `inventario.lote` (Detalle en [06b Esquemas y DDL PostgreSQL](06b-esquemas-y-ddl-postgresql.md)) | Reemplaza el prefijo de tabla; delimita el dominio y evita colisiones |
| Modelos y tablas en español, snake_case, en singular: `PedidoVenta`, `Lote`, `GuiaTransferencia` | Tabla final vía `Meta.db_table`: `ventas.pedido_venta`, `inventario.lote` |
| Columnas en español, snake_case, sin abreviaturas ambiguas y **sin tilde/ñ en identificadores** (`anio`, no `año`): `cantidad`, `precio_unitario`, `fecha_vigencia` | Legible para el equipo y el servidor |
| Llaves foráneas: el campo se llama `<tabla>` y Django genera `<tabla>_id` (`proveedor_id`, `local_origen_id`) | Igual que genera Django |
| Booleanos de negocio en español (`activo`, `es_global`, `es_principal`, `es_predeterminada`); `is_superuser` reservado de Django | `activo = false` es el borrado lógico |
| Constraints UNIQUE y CHECK con sufijos `_uk` / `_ck` (`sales_factura_correlativo_uk`, `core_usuario_rol_ck`) | Nombres de constraint explícitos |
| La lógica de código que no es modelo (funciones, servicios, componentes React) **sí va en inglés** | `consume_material()`, `useLote()`, `<PriceMatrix />` |

### Estructura obligatoria de `class Meta` en los modelos

Para evitar que Django genere tablas con prefijos planos ambiguos (`catalog_material`) en el esquema por defecto, **todo modelo implementado por el Grupo de Base de Datos debe definir su `class Meta` con `db_table` calificado por esquema** (soportado por el backend propio `backend.common.pgschema`):

```python
from django.db import models
from backend.common.base_models import ActivoMixin, TimeStampedModel

class Material(TimeStampedModel, ActivoMixin):
    nombre = models.CharField("nombre", max_length=150)
    codigo = models.CharField("código", max_length=50)

    class Meta:
        db_table = "catalogo.material"  # Esquema + tabla explícitos en BD
        verbose_name = "material"
        verbose_name_plural = "materiales"
        ordering = ["nombre"]

    def __str__(self):
        return f"{self.codigo} - {self.nombre}"
```

## Tipos de datos

| Dato | Tipo | Notas |
| --- | --- | --- |
| Montos monetarios | `NUMERIC(14, 2)` + columna `moneda` (`USD` \| `VES`), nunca float | `DecimalField(max_digits=14, decimal_places=2)` |
| Cantidades de material | `NUMERIC(12, 4)` | Metros con décimas: 1.8 m, 0.35 m² |
| Porcentajes (margen, IVA, comisión) | `NUMERIC(5, 4)` | `1.3000` = 130 %, `0.1600` = 16 % |
| Textos de negocio | `VARCHAR(n)` con tamaño razonable | Sin `TEXT` donde un `VARCHAR` basta |
| Estado previo/posterior de datos | `JSONB` (con opción de índice GIN) | Snapshot de eventos auditados |
| Rutas de archivos | `VARCHAR(500)` (`url_archivo` / `ruta_archivo`) | Los PDFs y adjuntos viven en disco/storage, registrados en la tabla correspondiente |
| Claves primarias internas | `BigAutoField` (`BIGINT GENERATED BY DEFAULT AS IDENTITY`) | `DEFAULT_AUTO_FIELD = "django.db.models.BigAutoField"` |

## Reglas que cruzan todas las tablas de negocio

1. **Mixins comunes**: `creado_en`, `actualizado_en` (`TimeStampedModel`) y `activo` (`ActivoMixin`, borrado lógico).
2. **Borrado lógico**: nunca `DELETE` físico de datos de negocio. El registro "se elimina" poniendo `activo = false`; las consultas normales filtran `activo = true` (con acceso al histórico solo con permiso).
3. **Append-only para bitácoras y cambios de precio**: `bitacora_accion`, `bitacora_stock` y `historial_cambio_precio` bloquean `save()` sobre registros existentes y `delete()` lanzando `PermissionDenied` en el ORM.
4. **Numeración correlativa por `(tipo_comprobante, local_id, anio)`** en `nucleo.contador_correlativo` con bloqueo `SELECT ... FOR UPDATE`, para facturas, orden de producción, nota de entrega, guía de transferencia y demás comprobantes (RF-54).
5. **Multi-moneda**: todo monto lleva su `moneda` (`USD` | `VES`); el conversor usa la tabla `nucleo.tasa_cambio` con el tipo de cambio vigente; el monto equivalente en Bs. no se duplica.
6. **Movimientos de stock = transacción atómica**: descuento del origen, entrada del destino, registro en `bitacora_stock` y enlace con la guía de transferencia se graban en la misma transacción de BD.
7. **La fórmula de precio no se completa en triggers**: `precio_base × porcentaje_margen × (1 + porcentaje_iva)` ocurre en la capa de servicios de `pricing`; la BD garantiza `CHECK (porcentaje_margen > 0)` y `CHECK (porcentaje_iva >= 0)`.
8. **Excepción documentada — `cobro.anulado_en`**: la tabla `ventas.cobro` usa `activo = false` como borrado lógico estándar (cobro anulado), y complementa con `anulado_en TIMESTAMPTZ` para registrar el momento exacto de anulación. Es la única tabla con este campo adicional; el patrón no se replica a otras tablas.

## Referencias débiles (polimórficas)

Cuando una tabla apunta genéricamente a entidades de distintos módulos sin FK rígida, se usa el patrón `<contexto>` + `<contexto>_id` o `db_constraint=False`:

| Campo(s) | Tabla | Qué representa |
| --- | --- | --- |
| `modulo`, `entidad`, `entidad_id` | `auditoria.bitacora_accion` | Módulo, entidad y ID del objeto auditado |
| `entidad_tipo`, `entidad_id` | `documentos.documento` | Tipo y ID de la entidad origen |
| `lote_id`, `producto_id` | `auditoria.bitacora_stock` | Lote, producto o material afectado |
| `pedido_venta_id`, `movimiento_stock_id` | `produccion.orden_produccion`, `produccion.consumo_material` | Trazabilidad débil entre producción, ventas e inventario |
| `vendedor_id`, `item_precio_id` | `ventas.pedido_venta`, `ventas.linea_pedido` | FK `db_constraint=False` hacia `rrhh` y `precios` |
| `usuario_id` | `rrhh.trabajador` | `OneToOneField` `db_constraint=False` hacia `nucleo.usuario` |

## Índices y performance

| Índice | Sobre | Para qué |
| --- | --- | --- |
| `(local_id, material_id)` WHERE `material_id IS NOT NULL` y `(local_id, variante_id)` WHERE `variante_id IS NOT NULL` | `inventario.stock` | Una sola fila de saldo por clave; vistas de stock por local |
| `(local_id, material_id)` | `inventario.lote` | Resolución de lotes disponibles |
| `(numero_lote)` UNIQUE | `inventario.lote` | Trazabilidad del rollo o partida |
| `(local_id, creado_en DESC)` | `inventario.movimiento_stock` | Historial de stock en orden inverso |
| `(estado, local_id)` / `(estado, local_origen_id)` | `ventas.pedido_venta`, `produccion.orden_produccion` | Tableros de pedidos y producción |
| `(tipo_documento, local_id, anio, correlativo)` UNIQUE | `documentos.documento` | Numeración correlativa y repositorio |
| `(cargo) WHERE activo` | `rrhh.trabajador` | Catálogo de personal activo por cargo |
| `(material_id, proveedor_id, registrado_en DESC)` | `compras.historial_precio_proveedor` | Comparador de precios |
| `(usuario_id, creado_en DESC)` | `auditoria.bitacora_accion` | Bitácora de usuario en orden inverso |
| `(local_origen_id, creado_en DESC)` y `(producto_id, creado_en DESC)` | `auditoria.bitacora_stock` | Bitácora de stock |

## Integridad y estados

- **Estados de negocio** (lote, pedido, transferencia) se representan con `VARCHAR(n)` + constraint `CHECK` en BD; en Django, mediante `TextChoices`. Evita estados inválidos a cualquier nivel.
- **La máquina de estados del pedido** (`COTIZADO → CONFIRMADO → EN_PRODUCCION → LISTO → ENTREGADO → FACTURADO`) se regula en la capa de servicios; la BD solo asegura el `CHECK`.
- FK cruzadas entre esquemas solo si son relación de negocio declarada ([06 Modelo de datos](06-modelo-de-datos.md)); de lo contrario se guarda solo el `id` (sin FK) para respetar el límite del módulo.
- **`tasa_cambio` y `contador_correlativo` viven en `nucleo`**: son infraestructura común. Lecturas de otras apps van vía la capa de servicios o FK de lectura (`cobro` y `factura_compra` guardan `tasa_aplicada_id` como evidencia de la tasa usada).
- Sin triggers de negocio en fase 1: la lógica vive en los servicios de Django. Los triggers quedan como herramienta de refuerzo si la auditoría requiere bloqueo absoluto.

## Migraciones y esquemas

- Cada módulo aplica `makemigrations`/`migrate` de su app; las migraciones se ejecutan en orden de dependencia (`nucleo` primero).
- Django escribe el esquema con `Meta.db_table = 'ventas.pedido_venta'` mediante `backend.common.pgschema`; no se usan `search_path` ni bases de datos separadas — todo el negocio vive en una BD, dividida por esquemas ([06b Esquemas y DDL PostgreSQL](06b-esquemas-y-ddl-postgresql.md)).

## Backups y ambiente

- Backup diario `pg_dump` comprimido, con retención de 30 días; probado cada mes (RNF-06). El `pg_dump` captura **todos los esquemas** en un solo volcado.
- 3 ambientes: `dev`, `staging` (opcional), `prod` con credenciales separadas y variables de entorno.
